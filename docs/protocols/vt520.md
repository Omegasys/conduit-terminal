# VT520 Terminal Protocol

## Overview

VT520 is a later DEC terminal protocol family extending the VT-series feature set.

Conduit supports VT520 compatibility as part of its terminal protocol subsystem. The implementation should build on the shared ANSI, VT, and DEC protocol infrastructure rather than creating an isolated terminal implementation.

The implementation lives under:

```text
src/terminal_protocols/
└── vt520/
```

## Design Goals

Conduit's VT520 implementation should:

* Provide practical VT520 compatibility.
* Reuse the common terminal parser.
* Preserve relevant DEC terminal semantics.
* Support advanced character and display behavior.
* Integrate with Conduit's modern Unicode representation.
* Handle fragmented input safely.
* Reject or safely ignore malformed sequences.
* Remain efficient under heavy terminal output.

## Layered Architecture

VT520 should build upon existing protocol layers:

```text
ANSI
 ↓
VT100
 ↓
VT220
 ↓
VT320
 ↓
VT420
 ↓
VT520
 ↓
Common terminal model
 ↓
Renderer
```

Only behavior that is genuinely specific to VT520 should require separate implementation.

## Parser

The VT520 parser should operate on the shared streaming parser.

It should recognize supported:

* C0 controls
* C1 controls
* ESC sequences
* CSI sequences
* OSC sequences
* DCS sequences
* DEC private modes
* VT520-specific sequences

A sequence may be split across multiple PTY reads and must still be parsed correctly.

## Terminal State

VT520 protocol operations should update Conduit's internal terminal state.

The state may include:

* Cursor position
* Character attributes
* Character sets
* Screen contents
* Scroll regions
* Terminal modes
* Keyboard modes
* Insert mode
* Wrap mode
* Saved cursor state
* Alternate-screen state
* Device attributes

The renderer should consume this state instead of implementing VT520 semantics itself.

## Character Sets

VT520-era terminal applications may depend on advanced character-set functionality.

Conduit should provide a compatibility layer capable of translating supported terminal character sets into its internal text representation.

The protocol layer should remain independent from fonts and glyph rendering.

## Display Attributes

Where relevant, Conduit should represent VT520 display attributes in the terminal cell model.

This may include:

* Bold
* Underline
* Reverse video
* Blink
* Color
* Width-related attributes
* Height-related attributes
* Other supported DEC display attributes

## Keyboard Modes

VT520 applications may depend on terminal-specific keyboard behavior.

Conduit should maintain keyboard modes independently from physical input devices.

```text
Keyboard
    ↓
Input manager
    ↓
Terminal keyboard mode
    ↓
VT520 encoder
    ↓
PTY
```

## Device Identification

Applications may query terminal capabilities.

Conduit should provide configurable responses for supported device-attribute requests.

Responses should identify the configured compatibility behavior without exposing unrelated host information.

## Modes

VT520 modes should be represented as explicit terminal state.

Mode changes may affect:

* Keyboard input
* Cursor behavior
* Screen behavior
* Wrapping
* Scrolling
* Mouse reporting
* Character interpretation

Changes should be observable through the event bus when other components need to react.

## Unsupported Hardware Behavior

Some historical VT520 functionality depended on physical terminal hardware.

Conduit should distinguish between:

* Features that have direct software equivalents.
* Features that can be safely approximated.
* Features that are obsolete hardware behavior.
* Features that should simply be ignored.

Unsupported hardware behavior should not cause a terminal session to fail.

## Security

All VT520 control sequences originate from terminal input and must be treated as untrusted.

Conduit should enforce:

* Sequence length limits
* Parameter limits
* Safe parser state transitions
* Resource limits
* Safe handling of strings
* Security policy for potentially dangerous control features

Security enforcement should be centralized where possible.

## Performance

The VT520 implementation should:

* Parse incrementally.
* Minimize allocations.
* Reuse parser buffers.
* Batch state changes.
* Avoid unnecessary renderer updates.
* Bound potentially untrusted input.

## Testing

Tests should cover:

* Cursor behavior
* Screen operations
* Scrolling
* Character attributes
* Character sets
* Keyboard modes
* Device attributes
* DEC private modes
* Reset behavior
* Fragmented sequences
* Malformed sequences
* Unsupported features

Tests should primarily verify resulting terminal state.

## Integration

VT520 integrates with:

* ANSI
* VT100
* VT220
* VT320
* VT420
* DEC protocol handling
* Terminal core
* PTY
* Input manager
* Screen model
* Scrollback
* Renderer
* Recording
* Diagnostics
* Security
* Event bus
* Flow View

## Conduit Implementation Principle

VT520 support provides compatibility with a later DEC terminal model while preserving Conduit's modern internal architecture.

Protocol compatibility belongs in the protocol subsystem. Terminal state belongs to the terminal core. Rendering belongs to the renderer.
