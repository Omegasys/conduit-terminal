# VT220 Terminal Protocol

## Overview

VT220 is a DEC terminal protocol and terminal behavior family that extends the capabilities associated with earlier VT-series terminals.

Conduit supports VT220 compatibility through its terminal protocol subsystem.

The implementation lives under:

```text
src/terminal_protocols/
└── vt220/
```

VT220 functionality should build on shared VT100 and ANSI infrastructure wherever protocol semantics overlap.

## Design Goals

Conduit's VT220 implementation should:

* Provide practical VT220 compatibility.
* Reuse common terminal parsing infrastructure.
* Support relevant VT220 control sequences.
* Preserve character and terminal mode semantics.
* Integrate with Conduit's Unicode and rendering architecture.
* Safely handle malformed sequences.
* Remain compatible with remote terminal applications.

## Architecture

VT220 support should not duplicate the entire terminal parser.

Instead:

```text
PTY byte stream
      ↓
Protocol parser
      ↓
ANSI / VT / DEC recognition
      ↓
VT220-specific handling
      ↓
Common terminal operations
      ↓
Terminal state
      ↓
Renderer
```

Shared behavior should be implemented once whenever possible.

## Control Sequences

VT220 introduces and extends terminal control mechanisms beyond the original VT100 behavior.

Conduit should support the VT220 sequences required for practical application compatibility.

Supported operations should be converted into internal commands rather than directly modifying renderer state.

## Cursor Control

VT220 applications may depend on:

* Cursor positioning
* Relative cursor movement
* Cursor save and restore
* Cursor visibility
* Cursor style-related behavior where applicable
* Scrolling-region interaction

Cursor operations should be handled by the terminal core.

## Display Control

Conduit should support VT220 display operations including appropriate mechanisms for:

* Clearing portions of the display
* Clearing lines
* Scrolling
* Selecting scrolling regions
* Switching display modes
* Resetting terminal state

The screen model should remain independent from the renderer.

## Character Sets

VT220 includes more sophisticated character-set support than earlier VT terminals.

Conduit should provide a character-set compatibility layer capable of handling supported VT220 mechanisms.

The character-set layer should feed into the common text representation used by the renderer.

## National Replacement Character Sets

Where relevant to VT220 compatibility, Conduit may provide support for historical character-set mechanisms.

These should be implemented as protocol translation rather than embedded into the rendering backend.

This separation makes it possible to support historical applications without constraining modern Unicode rendering.

## Keyboard Modes

VT220-compatible applications may request different keyboard behavior.

Conduit should represent keyboard modes explicitly.

Keyboard input should flow through:

```text
Physical keyboard
      ↓
Input manager
      ↓
Terminal mode state
      ↓
VT220 keyboard encoding
      ↓
PTY
```

This allows the same terminal core to support different protocol families.

## Device Attributes

Terminal applications may query the terminal for supported capabilities.

Conduit should provide configurable responses appropriate to the selected terminal compatibility mode.

Capability responses should not expose unnecessary host information.

## Terminal Identity

Terminal identity should be configurable independently from the parser.

For example, a user may configure a session to advertise a particular terminal type while Conduit internally supports a broader protocol set.

## Security

VT220 control sequences must be processed as untrusted terminal input.

Security handling should include:

* Input-size limits
* Safe parser state transitions
* Validation of parameters
* Protection against malformed sequences
* Restricted dangerous control features
* Diagnostics for unsupported or suspicious sequences

## Performance

VT220 processing should use the same streaming architecture as other terminal protocols.

The implementation should avoid unnecessary conversions between protocol-specific representations.

Large terminal output should be processed in batches whenever practical.

## Compatibility Testing

The VT220 implementation should include tests covering:

* Cursor operations
* Screen operations
* Character attributes
* Character sets
* Keyboard modes
* Device queries
* Reset behavior
* Scrolling regions
* Malformed sequences
* Fragmented sequences

Compatibility tests should compare resulting terminal state rather than renderer-specific output whenever possible.

## Integration

VT220 support integrates with:

* Terminal core
* ANSI parser
* VT100 compatibility
* DEC protocol handling
* PTY
* Input manager
* Screen model
* Scrollback
* Renderer
* Recording
* Diagnostics
* Security
* Event bus

## Conduit Implementation Principle

VT220 compatibility should be implemented as a capability layer over the shared terminal architecture.

The goal is to preserve expected application behavior without creating separate terminal implementations for every historical terminal model.
