# VT100 Terminal Protocol

## Overview

VT100 is a historically important terminal protocol associated with the DEC VT100 family of terminals.

Conduit provides VT100 compatibility as part of its terminal protocol subsystem so that software designed around traditional VT100 behavior can operate correctly.

The implementation lives under:

```text
src/terminal_protocols/
└── vt100/
```

VT100 support should share as much infrastructure as possible with the common ANSI and DEC protocol implementations.

## Design Goals

Conduit's VT100 implementation should:

* Provide practical VT100 compatibility.
* Preserve historical terminal semantics where relevant.
* Reuse the common parser infrastructure.
* Translate VT100 behavior into Conduit's internal terminal model.
* Handle fragmented PTY output.
* Safely handle malformed sequences.
* Avoid unnecessary compatibility differences between local and remote sessions.

## Relationship to ANSI

VT100 and ANSI terminal behavior overlap substantially.

Conduit should avoid maintaining completely independent implementations of functionality that is shared between ANSI and VT100.

Instead:

```text
                    ┌── ANSI
Byte stream ────────┼── VT100
                    └── DEC extensions
                         ↓
                  Common parser/state
                         ↓
                   Terminal state
```

Protocol-specific behavior should be applied where semantics differ.

## Control Characters

VT100-compatible applications rely heavily on traditional control characters.

Conduit should correctly process supported controls including:

* BEL
* BS
* HT
* LF
* VT
* FF
* CR
* ESC

Control characters should be processed independently from printable character rendering.

## Cursor Behavior

VT100 compatibility includes cursor-oriented terminal operations.

Conduit should support the relevant operations for:

* Cursor movement
* Absolute cursor positioning
* Relative movement
* Cursor save and restore
* Cursor visibility
* Screen positioning

Cursor state should be stored by the terminal core.

The renderer should only consume the resulting state.

## Screen Management

VT100 applications commonly expect control over terminal display regions.

Conduit should support the relevant VT100 operations for:

* Clearing display regions
* Clearing lines
* Scrolling
* Selecting scrolling regions
* Moving the cursor
* Resetting terminal state

Scrolling regions should be represented internally rather than implemented as renderer-specific behavior.

## Character Attributes

VT100-style applications may use terminal attributes for text presentation.

Conduit should translate supported attributes into its common style representation.

This representation can then be consumed by any renderer backend.

## Character Sets

VT100 terminals support character-set mechanisms that differ from modern Unicode terminal assumptions.

Conduit should provide a compatibility layer for relevant VT100 character-set behavior.

The protocol layer should remain separate from the final font and glyph-selection system.

```text
VT100 character selection
        ↓
Conduit character representation
        ↓
Text shaping
        ↓
Font selection
        ↓
Renderer
```

## Alternate Screen

Applications such as text editors and full-screen terminal programs may depend on alternate-screen behavior.

Conduit should support the appropriate terminal mode transitions required by applications targeting VT100-compatible environments.

Alternate-screen state should remain part of the terminal session rather than the renderer.

## Reset Behavior

VT100-compatible reset operations should reset the appropriate terminal state without unnecessarily destroying unrelated Conduit session state.

A terminal reset may affect:

* Cursor state
* Character attributes
* Modes
* Scroll regions
* Screen contents
* Character-set state

The session itself should remain under the control of the session manager.

## Compatibility

Conduit should prioritize practical compatibility with software that identifies itself as a VT100-compatible terminal.

Applications should be able to query terminal characteristics through supported mechanisms.

The configured terminal identity should therefore be independently configurable from the internal protocol implementation.

## Security

VT100 escape sequences originate from programs running inside the terminal.

They must therefore be treated as untrusted input.

Conduit should apply its terminal security controls to VT100 sequences just as it does to ANSI and later DEC protocols.

Malformed or excessively large sequences should not be able to destabilize the terminal process.

## Performance

VT100 parsing should share the high-performance streaming infrastructure used by other terminal protocols.

The implementation should support:

* Incremental parsing
* Buffered input
* Minimal allocations
* Batched state updates
* Large output streams
* Diagnostics for malformed sequences

## Integration

VT100 support integrates with:

* Terminal core
* PTY
* Screen state
* Cursor state
* Scrollback
* Renderer
* Input handling
* Recording
* Diagnostics
* Security
* Event bus

## Conduit Implementation Principle

VT100 support exists to provide compatibility, not to force the rest of Conduit to behave like a historical physical terminal.

Historical behavior should be faithfully represented where applications depend on it while still allowing Conduit to use its modern internal architecture.
