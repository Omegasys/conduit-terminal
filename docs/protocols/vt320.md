# VT320 Terminal Protocol

## Overview

VT320 is a later member of the DEC VT terminal family and extends the capabilities of earlier VT-series terminals.

Conduit supports VT320 compatibility through its terminal protocol subsystem.

The implementation lives under:

```text
src/terminal_protocols/
└── vt320/
```

VT320 support should reuse the common ANSI, VT100, and VT220 infrastructure while providing additional behavior where required.

## Design Goals

Conduit's VT320 implementation should:

* Support practical VT320-compatible applications.
* Reuse existing protocol infrastructure.
* Preserve relevant DEC terminal semantics.
* Support advanced terminal modes.
* Integrate with modern text rendering.
* Handle fragmented and malformed input safely.
* Remain efficient under heavy terminal output.

## Layered Architecture

VT320 support should be layered on top of common protocol functionality.

```text
                    ANSI
                      │
                    VT100
                      │
                    VT220
                      │
                    VT320
                      ↓
             Common terminal model
                      ↓
                  Renderer
```

This model minimizes duplicated parsing logic.

## Parser

The VT320 parser should consume a byte stream incrementally.

It should recognize:

* Control characters
* Escape sequences
* Control Sequence Introducers
* Device Control Strings
* Operating System Commands where supported
* VT320-specific sequences

The parser should never assume that an entire sequence arrives in a single PTY read.

## Cursor and Screen

VT320-compatible applications may use advanced cursor and screen-control behavior.

Conduit should support relevant operations involving:

* Cursor positioning
* Cursor movement
* Cursor visibility
* Screen clearing
* Line clearing
* Scrolling
* Scrolling regions
* Saved cursor state
* Terminal reset

The terminal core owns the resulting state.

## Character Sets

VT320 systems provide broader character-set functionality than earlier VT models.

Conduit should support the character-set mechanisms necessary for compatibility while maintaining a modern internal Unicode-oriented representation.

The conversion path should remain:

```text
VT320 character encoding
        ↓
Character-set translation
        ↓
Internal text representation
        ↓
Text shaping
        ↓
Renderer
```

## Double-Width and Double-Height Text

VT-series applications may use display attributes that alter character dimensions.

Where VT320 behavior requires them, Conduit should represent these attributes explicitly in the terminal cell model.

The renderer should interpret the resulting cell attributes.

Protocol parsing should not contain renderer-specific drawing code.

## Keyboard Handling

VT320 keyboard behavior may differ from modern terminal defaults.

Conduit should maintain explicit terminal keyboard modes.

Keyboard events should be converted according to the active protocol and terminal modes before being sent through the PTY.

## Device Queries

Applications may query terminal capabilities.

Conduit should provide configurable capability responses appropriate to the active compatibility mode.

Responses should be deterministic and should avoid leaking unrelated system information.

## Modes

VT320 introduces additional terminal modes and behavior beyond earlier models.

Conduit should maintain these modes in the terminal state and expose them to relevant components through the event system.

Mode changes may affect:

* Input encoding
* Cursor behavior
* Screen behavior
* Mouse handling
* Scrolling
* Character rendering

## Unsupported Features

Not every physical VT320 hardware capability needs to have a direct modern equivalent.

For unsupported features, Conduit should:

* Recognize the sequence when practical.
* Apply a compatible approximation when safe.
* Ignore irrelevant hardware-specific behavior.
* Record diagnostics when useful.

Unsupported behavior should not cause the terminal session to fail.

## Security

VT320 sequences are terminal input and therefore untrusted.

Conduit should protect against:

* Malformed control sequences
* Excessively long strings
* Parser state exhaustion
* Excessive terminal updates
* Unsafe control features
* Resource exhaustion
* Unexpected mode changes

Security decisions should be centralized in the terminal security subsystem rather than duplicated throughout the protocol implementation.

## Performance

VT320 support should use the same performance architecture as the other terminal protocols.

Important considerations include:

* Streaming parsing
* Reusable buffers
* Bounded sequence lengths
* Batched terminal updates
* Efficient parameter parsing
* Avoiding unnecessary allocations
* Efficient state transitions

## Compatibility Testing

The VT320 test suite should cover:

* Cursor movement
* Screen operations
* Scrolling
* Character attributes
* Character sets
* Keyboard modes
* Device queries
* Terminal modes
* Double-width and double-height attributes
* Reset behavior
* Fragmented sequences
* Malformed sequences
* Unsupported sequences

Tests should primarily validate terminal state and protocol responses.

## Integration

VT320 integrates with:

* ANSI
* VT100
* VT220
* DEC protocol handling
* Terminal core
* PTY
* Input manager
* Screen model
* Scrollback
* Renderer
* Recording
* Diagnostics
* Security
* Event bus
* Flow View

## Conduit Implementation Principle

VT320 support should extend the shared terminal protocol architecture rather than creating an isolated terminal implementation.

Historical compatibility belongs in the protocol layer; modern rendering, configuration, security, and session management remain responsibilities of the corresponding Conduit subsystems.
